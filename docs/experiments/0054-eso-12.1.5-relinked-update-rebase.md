# Experiment 0054: ESO 12.1.5 relinked-update rebase

- Date: 2026-09-30
- Outcome: **succeeded in static audit, source build, package fixtures, and
  installation; awaiting one natural user launch**
- Rollback: **not required; verified same-generation recovery backup present**

## Question

After the 2026-09-30 Steam update, the installed patcher reported the original
loader and the public 0.2.0 installer stopped with "ESO's MoltenVK call layout
changed". Did ESO change its embedded MoltenVK runtime or its use of it, or is
the new build a relocation that the patcher can support without changing the
validated runtime behavior?

The user also asked whether the unpatched post-update client's roughly
45--50 FPS, with less smoothness than the patched 60-FPS VSync baseline,
reflects a ZeniMax performance change.

## Hypothesis

The embedded MoltenVK object is unchanged and only its link placement and the
surrounding ESO layout moved. Falsified by any changed archive member, patch
signature, external reference kind/count, or GIPA/GDPA query-name multiset.

## Evidence

Static analysis, performed without launching any app:

- The public 0.2.0 archive check passed; its address-fixed `eso-compat-audit`
  failed first at `0x1a14680` because its patch table is absolute.
- All 17 12-byte patch signatures occur at a uniform +`0x1de7a0` shift.
  Matching the whole 0x4d00a-byte object `__text` found exactly one placement
  where every non-relocation byte matches; the only 188 differences are the
  opcode byte of `X86_64_RELOC_GOT_LOAD` sites (`8b` to `8d`), which is ld64's
  standard GOT-load-to-LEA relaxation.
- Xcode 27.0 (27A266a) `dyld_info -fixups` and the Command Line Tools copy both
  trap in `SymbolicatedImage::fixupTargetString` after printing all 275,882
  rebases of the new executable. A native decoder reproduced that rebase list
  exactly and in order, and matched `dyld_info` on three Bink dylibs and on
  chained/classic x86_64 fixtures.
- The 0.2.0 release auditor counts pointer references only from chained
  fixups and expected 657 of them, so the previous executable used chained
  fixups. This is an inference from the profile; the old executable is not
  retained.
- With the placement and slots recovered, the 40 external references and the
  GIPA 19 / GDPA 80 query-name multisets equal the 12.0.8 profile exactly.
- One apparent new direct call to `vkCreateDescriptorPool` at `0x101af0b33`
  is a byte-scan coincidence: disassembly from the enclosing function start
  places it at the last byte of `movq -0x18(%rbp),%rax` followed by
  `subq $0x10,%rax`. It is recorded under `rejected_unaligned`.
- ESO imports 13 Bink symbols; both Bink generations export all 13.

## Interpretation

Confirmed: ZeniMax did not change the embedded MoltenVK object or the Vulkan
entry points ESO calls. The update relinked the game with a different
toolchain/deployment configuration and shipped a newer Bink.

Inference: the unpatched post-update frame rate is the known unpatched
behavior with the preserved balanced settings (FINDINGS records 54--56 FPS
early and later 30--33 FPS degradation), not a ZeniMax MoltenVK improvement.
No evidence connects the update to this repository.

Hypothesis, untested: the older deployment target (10.13) can change AppKit
linked-on-or-after behavior. That could matter to the focus/activation
investigation in Experiment 0052, but there is no observation yet.

## Amendment 2026-09-30: build-probe log isolation

The side observation above is addressed on `main`; the original observation is
preserved.

- `teso4m4_open_production_log()` honours a source-maintenance
  `TESO4M4_LOG_DIR` override. When set, the bridge writes only
  `<dir>/bridge.log`; an empty, relative, missing, or non-directory value
  disables logging instead of falling back to the production or `/tmp` log.
- `scripts/build.sh` exports a temporary `TESO4M4_LOG_DIR` before any probe,
  asserts the smoke run's `RUN_START` and `SKIP: enable marker absent` land
  there, and fails if the production log's inode, size, or mtime changed.
  `smoke_proxy` refuses to load the bridge without the override.
- Public Status/Diagnostics choose the latest run that has any record other
  than `RUN_START` and `SKIP: enable marker absent`, and report newer ignored
  non-game loads separately. A marker-absent run with any other record stays
  reviewable. The installer fixture covers both cases and the probe-only log.
- With the installed 0.2.1-rc.1 bridge active and the legacy pristine Bink
  still the 12.0.8 generation, `build.sh` now reads (never modifies) the
  installer's hash-verified recovery backup as the build source.

Verification: fresh build (production log `stat` identical before and after,
isolation line PASS), 146 Python tests, installer fixture PASS. The two
probe runs remain in the production log as evidence; they were not removed.

Observation, not investigated here: the newest production run
`20260930T045240.104422000Z-pid25796` has no `log_source` field (0.2.0-based
bridge) and ended with `SKIP: selected target has no inactive pacing profile`.
It is not a marker-absent probe, so Status still treats it as the last launch.

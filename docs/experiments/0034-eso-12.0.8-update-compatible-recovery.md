# Experiment 0034: ESO 12.0.8 update-compatible recovery

- Date: 2026-08-11
- Outcome: **succeeded for update recovery and normal gameplay; cold-start reliability follow-up required**
- Rollback: **not required; validated bridge remains installed**

## Question

Can the 0.1.0 production bridge be safely reinstalled after the launcher
replaces the ESO executable, without requiring a new hand-maintained profile
when the embedded MoltenVK runtime and the bridge-facing call structure are
unchanged?

## Hypothesis

A relocation-tolerant compatibility audit should accept ESO 12.0.8 only if the
embedded MoltenVK, 17 patch signatures, complete old-runtime reference
boundary, and GIPA/GDPA query shape remain compatible. The installer should
then preserve the verified original-loader backup, attest the new executable
hash, and reinstall the same bridge. Any changed patch byte or call shape must
stop before mutation.

## Target and change set

- ESO macOS client 12.0.8, databuild `3288357`.
- Executable SHA-256:
  `a819aa2313e91676bdfa3987ae650d594a86faf2429ad56c736b5e6992680609`.
- Mach-O UUID: `0e6ea0ca-cac2-37c4-9834-cac2b8467950`.
- Replacement runtime: official MoltenVK 1.4.2, unchanged from 0.1.0.
- Release candidate installed for the runtime test: `0.1.1-rc.1`.
- Final installer candidate: `0.1.1-rc.2`; its bridge and replacement-runtime
  payload hashes are identical to RC1.

## Preflight

- `scripts/check-update.sh` reported `CURRENT` for the new selected target.
- The launcher repair had restored the active original Bink loader while
  leaving the prior patch marker, verified recovery data, caches, and companion
  files intact.
- Static comparison found both embedded MoltenVK archive members unchanged,
  all 17 patch targets unchanged, equivalent external-reference and proc-query
  shapes, and a uniform 48-byte source-site relocation.
- The complete source build, non-game bridge probes, update-tool unit tests,
  release transaction fixture, ZIP integrity checks, and a negative
  one-patch-byte compatibility-auditor test passed.

## Procedure

1. Rebased the exact selected profile to ESO 12.0.8 after the static audit.
2. Added a packaged native compatibility auditor and executable-hash
   attestation in the runtime marker.
3. Extended Install to recover both launcher-restored-original and
   bridge-retained update states from the verified backup.
4. Installed RC1 without changing settings or caches under the standing
   verified maintenance authorization.
5. The user launched through the normal Steam authentication path. The agent
   did not launch ESO, Steam, or the ZeniMax launcher.
6. After the user's report, inspected only non-destructive status, sanitized
   production bridge events, cache identity metadata, and crash-report
   presence.

## Evidence

The installed marker attests the ESO 12.0.8 SHA-256. Post-run status reports
the exact selected target, current bridge, current official MoltenVK 1.4.2,
verified active pipeline-cache identity, and preserved historical caches.

Three consecutive production-info runs were recorded approximately one minute
apart. Runs beginning at `20260811T142556`, `20260811T142655`, and
`20260811T142756` each record:

```text
runtime:            official MoltenVK 1.4.2
redirects:          17 Vulkan entry points active
ESO SHA-256:        a819aa2313e91676bdfa3987ae650d594a86faf2429ad56c736b5e6992680609
suppressed draws:   79
forward latch:      generation 2, ordinal 150, present-deadline
```

The user reported that the final start and gameplay worked normally. The user
also reported a recurring post-patch pattern: the first one or two starts may
show the pink splash and then run at approximately 10 FPS; quitting and
restarting ESO, and sometimes restarting the launcher, leads to clean normal
operation. No controlled FPS capture or per-start cache snapshot was prepared
for this run, so the approximate frame rate and causal attribution remain user
observations rather than telemetry.

## Result

The update-compatible recovery path succeeded on ESO 12.0.8. The packaged
runtime activated all 17 redirects against the newly attested executable,
reached the bounded compositor forward latch, and supported normal gameplay.
A deliberately changed patch byte was rejected as `INCOMPATIBLE_UPDATE` with
exit status 3.

The run did not establish deterministic first-start behavior. Repeated starts
were required before the user's normal result, despite all three runs reaching
the same high-level production bridge milestones.

## Interpretation

Confirmed: a game update that preserves the embedded runtime and the audited
bridge-facing structure no longer requires a hand-maintained absolute-address
allowlist or a new patcher release. The same installer can re-establish its
verified loader state and attest the updated executable. Structural or byte
changes still fail closed.

Confirmed: the observed low-FPS starts are not explained by total bridge
activation failure; all recorded starts reached the 17-entry-point active
state and compositor latch.

Hypothesis: cold Metal shader/pipeline compilation, pipeline-cache rewrite or
revalidation, launcher/process lifetime, or another startup-only resource
transition may distinguish the bad and good starts. This run did not collect
the per-start timing, cache-delta, Metal HUD, or process-state evidence needed
to choose among them.

## Rollback

No rollback was required. The exact 12.0.8-attested bridge remains installed,
and the independently verified original-loader backup remains available.
Settings and caches were not replaced during installation.

## Follow-up

Release 0.1.1 as the update-compatibility maintenance release. Make a bounded
cold-start experiment the next P0 gate: snapshot cache identity, size, and
mtime before every start; record launcher/ESO process boundaries and startup
timing; capture Metal HUD frame/GPU timing in a fixed scene; and compare the
first bad start with the first clean start before attempting any cache warm-up
or precompilation mechanism.

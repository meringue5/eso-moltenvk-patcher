# Experiment 0007: ESO 12.0.7 target rebase

- Date: 2026-07-20
- Outcome: **planned; static target rebase passed**
- Rollback: **not started; stale Experiment 0006 loader preserved**

## Question

Can the verified Experiment 0006 descriptor-compatibility bridge be rebased to
launcher-managed ESO 12.0.7 without changing its 17 redirects, HDR filters, or
MoltenVK controls?

## Hypothesis

If the update changed client content but retained the statically linked
MoltenVK layout, a new exact SHA-256 and UUID should be sufficient. This
hypothesis fails if any wrapper offset, patch byte, external reference, proc
slot, proc query route, embedded-runtime object, or non-game probe changes.

## Update boundary

At approximately 21:02 KST, the user opened the normal Steam launcher for the
prepared Experiment 0006 warm-cache repeat. Before ESO launched, the launcher
installed client 12.0.7, databuild `3281538`. Seven files in the app bundle were
rewritten at 21:02:59, including the executable, active Bink loader, bundled
MoltenVK archive, game manifest, and data payload.

The launcher UI had reached a Play button when inspected, but also displayed a

## Static target evidence

The update did not change the legacy MoltenVK object. Its SHA-256 remains
`7dfdcb34f8e1395410b8bd639c46398a1318429c5a9a6e53784356c86723a85a`,
and the bundled headers still report MoltenVK 1.0.18.

Analysis against the new executable established:

- the MoltenVK link delta remains `0x1a08490`;
- 162 old Vulkan text symbols yield the same 40 external references to exactly
  the same 17 manifest entries;
- MoltenVK 1.4.1 exports every externally referenced entry;
- the prior 17 offsets still identify the same wrappers, and all 17 exact
  12-byte patch preconditions are unchanged;
- the GIPA and GDPA slots remain `0x4b3be90` and `0x4b3be98`;
- static proc recovery finds 19 GIPA sites with 17 unique names and 80 GDPA
  sites with 65 unique names, with no unnamed site;
- comparison against the existing 100-name old/new runtime probes finds no
  missing result and no old-nonnull/new-null regression on ESO's query route.

Generating a target header from
`config/targets-eso-2026-07-20.json` changed only the expected SHA-256 and UUID;
the target count, offsets, names, and patch bytes are identical.

## Preserved installed state

The active loader still begins with the exact 44,400 bytes of the prepared
Experiment 0006 proxy, SHA-256
`fa8b89c2e090c36663f578e6a7d9fae557b0aebc6aa47a03ba4d9faeb3046550`.
The launcher expanded that file to 226,368 bytes with 181,968 zero-filled
trailing bytes, so its whole-file hash no longer identifies the built artifact.
Its embedded target hash is still the superseded SHA-256, and the bridge
constructor will skip patching on the new UUID. The marker and warm cache
remain preserved.
